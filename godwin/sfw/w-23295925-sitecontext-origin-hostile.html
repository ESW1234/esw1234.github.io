How it works

  1. Control: this page frames sitecontext with parent_domain set to its own origin. That is a legitimate embedder, so it must work. It writes a canary and reads it back to prove the plumbing.
  2. Attacker: a sandboxed iframe (sandbox="allow-scripts", no allow-same-origin) has an opaque null origin, so it is a real cross-origin sender. It frames sitecontext and sends SET_ITEMS, CLEAR and SET_OBJECTS.
  3. Verdict: the control reads storage again. Third-party storage is partitioned by top-level site, and both frames share this page's top-level site, so they see the same storage. In mode A, canary intact and nothing poisoned means PASS. Anything else means the check is missing or ineffective on that deployment.
  4. Mode B is the residual risk the fix does not close: an attacker that frames sitecontext with its own origin as parent_domain. Expect it to take effect until a CSP frame-ancestors header lands from Core.

Also check the console of the attacker's sitecontext frame (DevTools console context dropdown). With the fix, mode A shows Unexpected message source or origin for each message.
